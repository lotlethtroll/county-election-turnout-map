1. Introduction
1.1 Purpose
This document specifies how the County Election and Turnout Map (CETM) will meet the requirements set out in the requirements analysis (Stimson, 2026b). The requirements analysis described what the system must do from the user’s point of view. This specification takes each of those requirements and states it precisely enough to design, build, and test against, including the exact calculations, data rules, limits, and screen behavior. Every specification keeps the ID of the requirement it develops (for example, FR-3.2), so the two documents can be read side by side and each item can be traced into the design document.
1.2 Scope
The scope is unchanged from the requirements analysis. The first version covers Colorado’s 64 counties and the certified results and turnout of the 2022 and 2024 general elections, limited to the top-of-ticket race in each: Governor in 2022 and President in 2024. Other states and primary elections are designed for but not loaded in the first version. Precinct-level results, other races and ballot measures, demographic data, and trend charts remain out of scope.
One change follows instructor feedback on the requirements analysis. A working prototype is not required for this project, so objective OBJ-5, which called for a working version at a public web address by the end of the course, has been removed. This specification describes the complete system as designed. Hosting details are still specified because they shape the design, not because a deployed site is a course deliverable.
1.3 Intended Audience and Use
This document has four readers. The course instructor uses it to evaluate whether the system is planned completely enough to design. The classmate reviewing it acts as the customer and checks that nothing a user would need is missing. The developer uses it during the design phase, since every design decision has to trace back to a numbered specification here. The Data Maintainer uses Sections 5 and 6 to understand exactly which files the system accepts and how each value is calculated.
The CETM itself is intended for members of the public who want to understand how their county and their state voted and how many people turned out, without reading spreadsheets or PDF reports. Its likely users include voters checking their own county, students and teachers comparing counties or elections, and local reporters confirming a figure. It is an unofficial reference tool for reading certified results, not a source of official results or a tool for counting, auditing, or certifying an election. The site states this on every view (FR-4.3).
1.4 Why the Details Matter
Colorado’s own published files show why the requirements need this level of detail. For the 2022 general election, the Secretary of State’s turnout page calculates turnout as a share of active voters and reports 66.24% statewide, while the Governor results page for the same election calculates turnout as a share of all registered voters and reports 58.39% (Colorado Secretary of State, n.d.-b, n.d.-c). Both pages count 2,543,316 ballots cast, yet only 2,508,830 votes were cast for Governor, because some voters skipped that race. A system that copied whichever turnout column it found first, or divided candidate votes by ballots cast, would publish numbers that disagree with the official ones. The specifications below fix exactly which number is used for every value the site shows.
1.5 Definitions
Terms defined in the requirements analysis keep the same meaning here, including turnout, which is ballots cast divided by active registered voters. Table 1 adds terms that appear only in this specification.
Table 1
Additional Terms Used in This Specification
Term
Definition
Adapter
A small program written for one state that reads that state’s official files and converts them into the common county result format. Each state has its own adapter because each state publishes results differently.
Build
The step the Data Maintainer runs on their own computer to read source files, calculate values, run the validation checks, and write the data files the website loads.
Choropleth
A map in which each area is filled with a color based on a data value. The CETM map is a choropleth of counties.

The federal five-digit county code, made of a two-digit state code (08 for Colorado) and a three-digit county number. It is the key that joins each county’s results to its shape, and it is unique nationwide, so it works for every state.

A text format for map shapes that a web browser can read directly. County boundaries are converted to GeoJSON during the build.

A file that describes one state: its name, FIPS code, election office, county list, and elections. The website and the build read state details from this file instead of from program code.
Validation report
The list of checks the build runs on new data, with a pass or fail result for each, shown to the Data Maintainer.

2. System Overview
2.1 System Structure
The CETM has two parts that never run at the same time. The first is a data pipeline that the Data Maintainer runs on their own computer. It reads the official files for a state, converts them with that state’s adapter, calculates turnout and margins, runs the validation checks, and writes small data files. The second is the public website, which is made only of HTML, CSS, JavaScript, and those data files. The website has no server, database, or user accounts. Its map is drawn with D3.js, whose geographic module projects county shapes onto an SVG map and whose scale functions turn each county’s value into a fill color (Observable, n.d.). Because the site is entirely static files, it can be hosted through GitHub Pages, which publishes HTML, CSS, and JavaScript directly from a project repository and is available on public repositories with a free account (GitHub, n.d.).
2.2 Data Sources for Colorado
Colorado’s 2022 figures come from two pages in the Secretary of State’s 2022 abstract. The turnout page lists active voters, ballots cast, and turnout for every county, and the Governor results page lists each county’s votes for every Governor ticket (Colorado Secretary of State, n.d.-b, n.d.-c). The 2024 figures come from the files listed in the state results archive: a spreadsheet of 2024 general election turnout by precinct, which the adapter sums to county totals, and the 2023 to 2024 biennial abstract of votes, published as a PDF (Colorado Secretary of State, n.d.-a). County shapes come from the U.S. Census Bureau’s 1:500,000 county boundary file, a national file from which any single state can be extracted. The Census Bureau offers it as a shapefile, geodatabase, KML, or geopackage download (U.S. Census Bureau, 2026), none of which a browser reads directly, so the build converts the selected state’s counties to GeoJSON.
2.3 Design Constraints
The public site must be entirely static files so it has no server to run or pay for.
All tools must be free and open source, and all data must come from public government sources.
No state name, county count, file name, or other state-specific value may be written into the website code. All of it comes from the state configuration and data files.
Only certified results may be published.
The project is designed and documented by one developer within the course term.

5. Data Specifications
5.1 State Configuration
Each state has one configuration file containing the state name, its two-digit FIPS code, the name and web address of its election office, its list of counties by FIPS code and name, and its list of elections. Each election entry records an ID, the election date, whether it is a general or primary election, the party for a primary, the race shown, whether the results are certified, the source files, and the adapter that reads them. This file is what makes a new state or election a data change rather than a code change (FR-5.4, FR-5.5, NFR-4.2).
5.2 County Result Record
For each election, the build writes one record per county with these fields: county FIPS code, county name, active registered voters, ballots cast, votes for each candidate, total votes in the race, turnout, leader, runner-up, margin in points, and margin label. Active registered voters may be empty for a state that does not report them, in which case turnout for that state is shown as “No data” under FR-6.2 rather than calculated another way.
5.3 Calculation Rules
Turnout equals ballots cast divided by active registered voters, times 100. It is always calculated, never copied from a source turnout column, because Colorado’s own 2022 pages report turnout two different ways (66.24% and 58.39%).
A candidate’s share equals that candidate’s votes divided by the total votes cast in the race, not by ballots cast. In 2022, Colorado counted 2,543,316 ballots but 2,508,830 votes for Governor (Colorado Secretary of State, n.d.-b), so dividing by ballots would understate every candidate.
Margin equals the leader’s share minus the runner-up’s share, labeled with the leader’s party in a general election or name in a primary.
Statewide values are calculated from county totals and must match the official statewide figures (FR-5.2).
Values are stored at full precision and rounded to one decimal place only when displayed.

6.1 User Interfaces
The page has five areas. The header holds the site name, the status line (FR-2.5), and the election and view selectors, plus the state and party selectors when they apply (FR-2.4, FR-2.6). The map area holds the map, its legend, and the statewide summary (FR-1.1 to FR-1.5). The details panel opens beside the map on screens wider than a tablet and below it on narrower screens (FR-3, NFR-1.3). The county list sits below the map with a search box (FR-3.1). The footer holds the unofficial-site notice, the data update date, and a link to the About section (FR-4.3, FR-4.4). All controls are standard HTML buttons, select menus, and links, so they work with keyboards and screen readers without custom code (NFR-1.4). Error and “No data” messages appear in the map area in plain language (FR-6.1, FR-6.2, NFR-1.2).
The Data Maintainer’s interface is a command run in a terminal on their own computer. It prints each validation check with a pass or fail result and the county affected, and it ends with a clear statement of whether the data was published or the previous data was kept (FR-5.2, FR-5.3). The maintainer guide documents every command and message (NFR-4.1).
6.2 Software Interfaces
On the input side, each state’s adapter reads that state’s official file formats and produces the county result record in Section 5.2, and the boundary step reads the Census file and writes GeoJSON (NFR-6.1). On the output side, the build writes plain JSON and GeoJSON files with a fixed structure, so the web page never needs to know which state or source format the data came from (NFR-4.2). In the browser, the page uses D3.js to project the county shapes, draw them as SVG, and map values to colors (Observable, n.d.). D3 is served with the site’s own files. The site uses no other outside libraries, services, or application programming interfaces (NFR-5.2, NFR-9.2).
6.3 Communications Interfaces
The only network communication is the visitor’s browser requesting the site’s static files from the host over HTTPS (NFR-7.1). On first load, the browser downloads the state list, the selected state’s configuration and county shapes, and the newest election’s data file, staying under the 1 MB first-view limit (NFR-3.1). Other election files are downloaded only when selected and then kept in memory (NFR-3.2). The site sends no data back to any server, sets no cookies, and calls no outside services while it runs (NFR-9.2), so it keeps working even if a state election office later moves or renames its files.
6.4 Hardware Interfaces
The CETM has no special hardware. It must work on phones, tablets, and computers with screens from 320 pixels wide upward (NFR-1.3), and it must accept touch, mouse, and keyboard input, with every target at least 24 by 24 pixels or reachable from the county list (FR-3.1, NFR-1.4). The Data Maintainer needs only an ordinary computer able to run the free build tools (NFR-5.2).
7. Acceptance Criteria and Project Objectives
This project is graded on its planning and documentation, not on a finished product, so this section defines acceptance rather than reporting test results. Each specification above has an acceptance criterion, and together those criteria define when a built version of the CETM would meet the four remaining project objectives. OBJ-1, accurate official data, is met by the build validation in FR-5.2 and the value checks in NFR-2.1. OBJ-2, ease of understanding, is met by the test-user criterion in NFR-1.1. OBJ-3, usability by everyone, is met by the accessibility criteria in NFR-1.4. OBJ-4, readiness for other states and primaries, is met by the criteria in FR-5.4, FR-5.5, and NFR-4.2, which require new states and elections to work without changing website code. OBJ-5 was removed as described in Section 1.2.
8. Future Enhancements
The following are outside this version and will be discussed as possible enhancements in the final reflection: loading real data for states beyond Colorado and for primary elections, which the design already supports; precinct-level results; races other than the top of the ticket and ballot measures; population and demographic information; and trend charts across several elections.
