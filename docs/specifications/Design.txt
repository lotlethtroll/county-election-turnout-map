1. Introduction
1.1 Purpose
This document describes how the County Election and Turnout Map (CETM) will be built. The requirements analysis set out what the system must do from a user’s point of view (Stimson, 2026b), and the requirements specification stated each of those 50 requirements precisely enough to design against (Stimson, 2026c). This design specification takes the next step and answers the construction questions: which languages and tools are used, how the system is divided into parts, what every data file contains, what every screen and control looks like and how it behaves, and how each program component does its job. It is organized around the four models of a software design: data design, architectural design, interface design, and component-level design.
1.2 Scope
The scope is unchanged from the requirements specification. The first version covers Colorado’s 64 counties and the certified results and turnout of two general elections, limited to the top of the ticket in each: Governor in 2022 and President in 2024. The design supports other states and primary elections from the start, but only Colorado data is loaded in the first version. Because the course does not require a working prototype, this document designs the complete system rather than a partial build. Anything that is built later has to follow it.
1.3 Intended Audience
The course instructor reads this document to judge whether the system is designed completely enough to build. The classmate reviewing it acts as the customer and checks that the design delivers what the requirements promised and that nothing a user would need has been left out. The developer, who is also the author, uses it as the build plan, and the Data Maintainer uses Sections 3.2, 4, and 5.7 to understand how election data moves from an official file to the published map.
1.4 Traceability
Every design decision in this document points back to at least one numbered requirement from the requirements specification, written as its original ID (for example, FR-2.3 or NFR-1.4). Section 7 reverses that link: it lists all 50 requirements and names the design elements that satisfy each one, so a reader can confirm that no requirement was dropped between the two documents.

2. Languages, Tools, and Platform
The CETM uses JavaScript almost everywhere, so one language covers the website, the build pipeline, and every state adapter. The public site is written in HTML, CSS, and JavaScript modules with no front-end framework, as the requirements specification limits it to plain web code plus D3.js (NFR-5.2). D3 is a free, open-source JavaScript library for data graphics that works directly with web standards such as SVG and describes itself as a low-level toolbox rather than a charting library (Observable, n.d.-a). That fits this project, because the map needs exact control over every county shape, color, and keyboard behavior. The build pipeline runs on Node.js, a free, open-source, cross-platform JavaScript runtime (Node.js, n.d.), on the Data Maintainer’s own computer.
One step needs a second language. Colorado publishes its 2024 vote totals only inside the biennial abstract, which is a PDF, and its 2024 turnout as a precinct spreadsheet (Colorado Secretary of State, n.d.-a). Python’s pdfplumber library extracts text and tables from PDFs and is released under the MIT license, and its documentation notes that it works best on machine-generated files rather than scans (Singer-Vine, n.d.). A short Python script handles only that extraction and writes a CSV file, after which the JavaScript adapter takes over. Table 2 lists every language and tool.

3. Architectural Design
3.1 Architectural Style
The CETM follows the two-part structure set in the requirements specification. Part 1 is a build pipeline that runs only on the Data Maintainer’s computer. It is a pipe-and-filter design: each stage takes the output of the one before it, does one job, and passes the result on, which makes every stage small enough to check on its own. Part 2 is a static single-page application that runs in the visitor’s browser. It is a state-driven design: user actions change one shared store, and every screen component redraws from the store. The two parts share nothing at run time except the published data files, so the website never reads an official source file and the build never touches the website code (NFR-4.2). Figure 1 shows how the parts connect.

3.2 Build Pipeline
The Data Maintainer runs the pipeline with a single command for one state, such as npm run build -- co (FR-5.1). Figure 2 shows its seven stages. Stage 6 writes every new file to a staging folder, and stage 7 replaces the whole published folder for that state in one step, so the site never holds a mix of old and new files (NFR-2.2).

3.3 Website Architecture
The website loads one HTML page and one starting module. The starting module reads the list of states, loads the chosen state’s configuration, county shapes, and newest election, and then hands control to the store. Figure 3 shows what happens after that. A user action reaches a control or the map, which asks the store to change. If the change needs an election file that has not been loaded, the store asks the Data Loader for it and waits. When the data is ready, the store tells every screen component, and each one redraws only its own part of the page. Nothing on the page changes until the new data is in hand, which is how the map, legend, panel, and status line always agree with each other (FR-3.4, NFR-3.2).

4. Data Design
4.1 Data Model
Figure 4 shows the six kinds of records the system keeps and how they relate. A state has many counties and many elections. An election has many candidates and one result record for each county. Each county result holds one vote count for each candidate. The county’s five-digit FIPS code is the key that joins results to shapes, because county names are spelled differently from one source to the next while the FIPS code is unique nationwide. Every record is stored as JSON, which the browser reads natively, and there is no database.

Colorado’s published 2022 figures show how a county record is filled. The Secretary of State reports 296,776 active voters and 169,626 ballots cast in Adams County, for a turnout of 57.16%, and 5,750 active voters and 5,312 ballots in Yuma County, for 92.38% (Colorado Secretary of State, n.d.-c). 4.4 County Shape File
The Census Bureau offers its cartographic boundary files as Shapefile, geodatabase, KML, and geopackage downloads, at scales of 1:500,000, 1:5,000,000, and 1:20,000,000 (U.S. Census Bureau, 2026). The Boundary Processor uses the 1:500,000 national county file, keeps only the counties whose code starts with the state’s FIPS code, simplifies the shapes until the file is 500 KB or smaller (NFR-3.1), and writes GeoJSON. Each county shape keeps two properties, its FIPS code and its name. The national file is downloaded once and reused for every state.
4.5 Validation Report
Each build writes a plain text report to the reports folder and prints the same text on screen. The report lists every check from FR-5.2 with PASS or FAIL. Each failure names the county and both numbers involved, so the Data Maintainer can find the problem in the source file. The report ends with either "Published" or "Not published: the site still shows the previous data."
4.6 Calculation Rules
The Calculator applies the rules fixed in the requirements specification. Colorado’s own 2022 pages show why each rule matters. The turnout page divides ballots by active voters and reports 66.24% statewide, while the Governor page divides by all 4,355,778 registered voters and reports 58.39%, and both count 2,543,316 ballots against only 2,508,830 votes for Governor (Colorado Secretary of State, n.d.-b, n.d.-c).
Turnout = ballots cast / active registered voters x 100. If a state does not report active voters, turnout is left empty and shown as No data, never calculated another way (assumption A-2).
Candidate share = candidate votes / total votes in the race x 100, never divided by ballots cast.
Margin = leader’s share minus runner-up’s share. In a general election the label uses the leader’s party (D+4.2, R+11.0). In a primary it uses the leader’s name. Equal shares give the label Tie.
Statewide values are calculated from the county totals and must equal the official statewide figures (FR-5.2).
All values are stored at full precision and rounded to one decimal place only when displayed.

5.3 Color and Legend
Margin view uses a D3 threshold scale, which places shade boundaries at chosen values (Observable, n.d.-d). The boundaries fall at 5, 10, and 20 points on each side, giving four blue shades for a Democratic lead and four red shades for a Republican lead (FR-1.2). Turnout view uses a D3 quantize scale, which divides a range into equal segments, one for each shade (Observable, n.d.-c). Its range runs from the lowest to the highest county turnout in the loaded election, so for Colorado’s 2022 election it spans 57.16% to 92.38% instead of 0 to 100%. The legend reads its ranges from the same scale the map uses, so the two always match (FR-1.3).
County borders are white, 1 pixel wide. Every fill color was checked against white with the WCAG contrast formula and reaches at least 3:1, which is the non-text contrast level WCAG 2.2 sets for parts of a graphic needed to understand it (W3C, 2024; NFR-1.4). The lightest shades were darkened until they passed. Table 8 lists the colors and their measured contrast with white.

Color never carries information alone (NFR-1.5). Every value shown by color also appears as text in the tooltip, the details panel, and the county list, which follows the WCAG rule that color cannot be the only means of conveying information (W3C, 2024). Text is #1A1A1A on white, a contrast of 17.4:1. The keyboard focus indicator is a 3-pixel black outline with a 2-pixel white ring outside it. The white ring stands out against every map shade, since all of them pass 3:1 against white, and the black outline stands out against the white page.
5.4 Tooltip and Details Panel
The tooltip appears beside the pointer or the focused county and shows the county name and its value in the current view, in the form "[County name] County, D+4.2" or "[County name] County, 71.3%" (FR-1.4). It stays open while the pointer is over it and closes with Escape. The details panel shows, from top to bottom, the county name, turnout to one decimal place, ballots cast, active registered voters, a results table of every candidate sorted by votes with party, votes, and share, the word Leader beside the leading candidate, and the margin under the table (FR-3.2, FR-3.3). Numbers use thousands separators.

5.6 About Section
The About section sits below the county list and is reached from a footer link. It lists every data source by name, publisher, link, and retrieval date (FR-4.1, NFR-9.1), defines turnout and margin in plain words (FR-4.2), and states that the site sets no cookies and runs no analytics, while noting that GitHub Pages logs visitor IP addresses for security purposes (GitHub, n.d.-a; NFR-9.2). 5.7 Data Maintainer Interface
The Data Maintainer works through a command line, described step by step in the maintainer guide (NFR-4.1). A normal update has four steps: place the new official files in the state’s sources folder, list the election in the state configuration, run the build command, and read the report. The report for a failed build looks like the example below, which shows the situation from Scenario 2 in the requirements analysis, where one county name in a source file does not match the configuration.
CETM build: Colorado (08), election 2024-general-president
[PASS] Configuration loaded, election marked certified
[PASS] Source files found (2 of 2)
[FAIL] County names: 1 row did not match any configured county
       turnout file, row 12: "Clear Creek Co."
[FAIL] Every configured county appears exactly once: 63 of 64
       missing: 08019 Clear Creek
Not published: the site still shows the previous data.

The fix is to add "Clear Creek Co." to that county’s other spellings in the configuration and run the build again. No code changes.
5.8 External Interfaces
The interfaces set out in the requirements specification are built as follows. The software interface on the input side is the adapter, which reads XLSX through SheetJS, saved HTML tables through the Node.js file system, and PDF tables through the pdfplumber script (NFR-6.1). The communications interface is HTTPS GET requests from the browser to GitHub Pages, and nothing else: the site calls no outside service while it runs (NFR-9.2). The hardware interface requires only a browser on a phone, tablet, or computer with touch, mouse, or keyboard input (NFR-5.1, NFR-6.2).

6.2 Store (C-2)
The store is the center of the website. It is the only place view state can change, which means no two components can ever disagree about what is selected. When an election change needs a file that is not in memory, the store waits for the Data Loader before telling anyone, so the page goes from the old view to the new one in a single redraw.
function setState(changes):
    next = copy of current state with changes applied
    if next.electionId differs from current.electionId:
        loadStatus = loading
        data = await dataLoader.getElection(next.stateAbbr, next.electionId)
        if data failed: loadStatus = error; notify subscribers; stop
        if next.selectedFips has no record in data: keep it selected
            (the details panel shows "No results for this county")
    current = next; loadStatus = ready
    for each subscriber: subscriber.render(current, data)

6.3 Data Loader (C-3)
The Data Loader requests an election file only the first time it is selected and keeps it in memory after that (NFR-3.2). If a request fails, it does not keep the failure, so the Try Again button simply asks again (FR-6.1).
cache = empty map
function getElection(state, id):
    key = state + "/" + id
    if key in cache: return cache[key]
    response = fetch("data/" + state + "/" + id + ".json")
    if response is not OK: return failure     (nothing is cached)
    cache[key] = parsed response
    return cache[key]

6.4 Scales and Map View (C-4, C-5)
C-4 builds a fresh scale each time the election or view changes. For margin, it turns each county’s margin into a signed number, positive for a Democratic lead and negative for a Republican lead, and passes it to a threshold scale with boundaries at -20, -10, -5, 0, 5, 10, and 20. A tie skips the scale and gets the neutral gray. For turnout, it finds the lowest and highest county turnout and builds a six-shade quantize scale across that range. C-5 then sets each county’s fill from its record, or the No data pattern when there is no record. When the map area changes size, C-5 calls the D3 projection’s fitSize method with the new width and height and the state’s county shapes, which resets the projection so the whole state fills the area (Observable, n.d.-b).
function fillFor(county, view, scale):
    if county has no record:      return NO_DATA_PATTERN
    if view is turnout:
        if turnout is empty:      return NO_DATA_PATTERN
        return scale(turnout)
    if marginLabel is "Tie":      return TIE_GRAY
    signed = margin if leader party is D, otherwise -margin
    return scale(signed)

6.5 Calculator (C-21)
The Calculator works from vote counts only. It never reads a published percentage, which is what keeps Colorado’s two different turnout figures from leaking into the map (Section 4.6).
for each county record r:
    r.raceTotal = sum of r.votes
    r.turnout   = r.activeVoters ? r.ballotsCast / r.activeVoters * 100 : empty
    for each candidate c: r.share[c] = r.votes[c] / r.raceTotal * 100
    order candidates by votes, highest first
    r.leader = first; r.runnerUp = second
    r.margin = r.share[leader] - r.share[runnerUp]
    r.marginLabel = margin is 0 ? "Tie"
                    : (general ? party of leader : name of leader) + "+" + margin
statewide = same steps applied to the sum of every county

6.6 Validator (C-22)
The Validator runs every check in FR-5.2 and always runs all of them, even after one fails, so the Data Maintainer sees every problem in one report instead of one per run.
checks:
    every configured FIPS appears exactly once in the results
    no row is left unmatched by the normalizer
    sum of county ballotsCast = official statewide ballots cast
    for each candidate: sum of county votes = official statewide votes
    no count is missing or negative
    every turnout is between 0 and 100
    the election is marked certified
publish only if every check passed

6.7 Colorado Adapter (C-18, C-19)
The Colorado adapter handles the three file types Colorado uses. For 2022, it reads the turnout table and the Governor table saved from the Secretary of State pages, taking active voters and ballots from the turnout page and candidate votes from the Governor page (Colorado Secretary of State, n.d.-b, n.d.-c). For 2024, it reads the precinct turnout spreadsheet through SheetJS and sums precincts to county totals, then reads the presidential table that C-19 extracted from the biennial abstract PDF (Colorado Secretary of State, n.d.-a). If the PDF extraction misreads a number, the statewide totals check in C-22 fails, so an extraction error cannot reach the published site.

8. Design Decisions and Alternatives
Table 12 records the choices that shaped the design most and what was considered instead, so a reviewer can see why the design looks the way it does.
Table 12
Design Decisions
Decision
Alternative rejected
Reason
Static files, no server
A server with a database
Results change only after an election is certified, so nothing needs to be computed on request. A static site costs nothing and has no server to secure (NFR-7.2).
Plain JavaScript modules
A front-end framework such as React
The page has one screen and about fifteen components, and the requirements limit the site to plain web code plus D3 (NFR-5.2).
SVG map
Canvas drawing
Each county in an SVG map is its own page element that can take keyboard focus and a text label. A canvas is one flat image that screen readers cannot see into (NFR-1.4).
GeoJSON shapes
TopoJSON, a smaller format
D3 reads GeoJSON directly with no extra library, and Colorado’s simplified shapes fit inside the 500 KB limit without it (NFR-3.1).
D3 shipped with the site
Loading D3 from a public CDN
A third-party outage cannot break the map, as dependency D-3 requires.
Calculate in the build
Calculate in the browser
Every value is checked against official totals before anyone sees it, and the browser does less work (NFR-2.1, NFR-3.2).
Python only for PDFs
All Python, or all JavaScript
Keeping one language for nearly everything makes the project easier to maintain, and pdfplumber is the tool built for PDF tables (NFR-6.1).
